So the runner meets the gate with many small rounds (L3) and not with one large room (L2's burst, L4), where the cost grows with the room's size. Night chain 2026-11-21/22, piece FAN-OUT (no code): its first lever, encoding each room frame once, is what the server already does: socket.io's adapter encodes a broadcast once and pre-computes its WebSocket frame (`wsPreEncodedFrame`), which engine.io hands to each socket's `ws` sender as it is (`sendFrame`); the profile's 43 s in `writev` are the one write per frame and socket that remains. Corking a socket while a committed batch goes out would join only the frames one socket gets in the same tick (a guesser's acknowledgement and own answer, about 0.26 guesses a second a player at L4), against the room frames every one of the 1 100 sockets gets up to ten times a second: a few per cent, not the halving the piece asked for, so it was not built. What would halve L4 is fewer room frames (a longer merge window than T49's 100 ms, which changes when clients get them) or writing from more than one process (the sockets spread over worker processes with socket.io's cluster adapter, the round's thread encoding once and handing the frame on), both outside the piece's rule (the same frames at the same times, one mechanism); the owner decided on 2026-11-21 to build neither now and to decide on the reference VPS with the load gate (O123).

## Needed from the website

Found in the dress rehearsal of 2026-11-06 (website `master` at `82e9e30`, which holds `feat/embedded-games` `468aaca`; Mini Games `feat/website-mode`; nginx mode on a fresh Ubuntu 24.04 machine).

1. **The login does not come back to the game.**
   - Step: a guest in the game clicks "Sign in" (or the chat's "Log in"), logs in on the website's login page.
   - Request: `GET /games/mini-games/auth/website?next=%2Fgames%2Fmini-games%2F` → 302 to `/login?next=%2Fgames%2Fmini-games%2Fauth%2Fwebsite%3Fnext%3D%252Fgames%252Fmini-games%252F`; then the login form (`POST /api/auth/login`, 200).
   - Answer: the website's own app moves to `/games/mini-games/auth/website?next=%2Fgames%2Fmini-games%2F` inside the page (`navigate(safeNext(next))` in `client/src/pages/LoginPage.jsx` `finish`) and shows its "Page not found"; no request reaches the game's sign-in route, so the member is not signed in to the game. A reload of that address signs in at once.
   - Expected: a full page load of `next` when it is not one of the website's own app routes (for example `window.location.assign(next)` for paths under `/games/`), so the proxy's sign-in route runs and the member lands back on the game page. The same `navigate(safeNext(next))` is in `RegisterPage.jsx` and `DiscordSignupPage.jsx`; the Discord login's server-side redirect (`server/src/discord/routes.js`) is not affected. The same holds for Bingo at `/games/bingo/`.
