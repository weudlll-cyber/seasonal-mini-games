# Decisions

Owner decisions, technical decisions with their reasons, security decisions, and rejected approaches. A decision is changed only by a task that says so. When it is changed, the old entry stays and is marked as superseded.

Each entry: its id, its date (an owner decision: the day decided; any other: the day it was first recorded) and its text, then its reason or where it is applied. Until 2026-11-17 this file was a set of tables; the same entries in that form are in git history (`git show 592592e:docs/DECISIONS.md`).

## 2. Technical decisions

T87–T100 were numbered T69–T82 on `night/2026-10-27` until it was brought up to date with `feat/guess-the-number` on 2026-11-01 (the feat branch had used those numbers too); every reference was renumbered, except the header comment of migration `0006_leaderboards.sql`, which still says T70 for what is now T88, because a published migration is never changed (its checksum is recorded).

- **T1** (2026-10-24): Names: package scope `@smg/*`, env prefix `SMG_`, DB schema `smg`, CLI `smg`, install root `/opt/smg` (full list in 04 §2.2). _Reason:_ Parallel to Bingo's names, but distinct, so both can run on one server and one development machine without any shared name.
- **T2** (2026-10-24): One base path for the whole platform on the website: `/games/mini-games`. _Reason:_ The website's rule is that games live at `/games/<name>` (Bingo D6). The games here are modules of one app with one login and one lobby, so they get one path, not one per game.
- **T3** (2026-10-24): Local ports 3910 (server), 5410 (player client), 5411 (admin client), 5510 (PostgreSQL), 1110 / 8510 (Mailpit). Container-internal ports 3100 (app) and 9465 (metrics). _Reason:_ Every one differs from every Bingo port and from the off-limits list (10 §4). The container ports differ too, so that logs, snippets and network configs on a shared website network never mix the two apps up.
- **T4** (2026-10-24): One round actor per open round, on one instance, with a FIFO queue. Intents are appended synchronously in socket read order. `receiveSeq` is assigned when the actor takes an item. _Reason:_ Gives O4 exactly one ordering point. No `await` between read and append means no reordering inside the process.
- **T5** (2026-10-24): Group commit: events are written in batches (20 ms or 200 events). Acknowledgements and broadcasts are sent only after commit. _Reason:_ One transaction per guess would cost a round trip per guess at about 170 guesses a second. Batching keeps that low, while sending after commit means a crash can never undo an announced winner.
- **T6** (2026-10-24): Cooldown is a stored end time per player, checked in the queue. There is no timer per player. _Reason:_ O3's "no global tick" in code. Constant work per guess, nothing to schedule, trivially restart-safe.
- **T7** (2026-10-24): Per-round 256-bit seed from the CSPRNG. Bingo's HMAC-SHA256 counter DRBG with labels. Secrets derived and never stored. Seed encrypted with `SMG_ROUND_KEY`. _Reason:_ Reproducible and verifiable (the fairness proof, O9, needs it), nothing secret in a dump, one proven generator reused from Bingo. One key for seeds follows Bingo's built `SBR_SEED_KEY`.
- **T8** (2026-10-24): Game-module contract in `packages/game-sdk`. Games live in `games/<game>`. `games/registry.ts` is the only place that names a game. Winning and placings stay in the platform. _Reason:_ Maintainability (priority 1): adding a game touches no platform code. O4 and O5 are inherited by every later game unchanged.
- **T9** (2026-10-24): Load tests use a Node.js driver with `socket.io-client` (`load/guessStorm.mjs`), not k6. _Reason:_ Bingo specified k6 but built a Node.js driver (`load/drawLatency.mjs`), which worked. k6 needs an extension for the Socket.IO protocol. One language for all code.

## 3. Security decisions

- **S1** (2026-10-24): The cooldown is enforced only on the server, per account (not per socket), at server receive time. _Reason:_ Clients can be changed. Several sockets or the HTTP fallback must not multiply the rate (05 §2).
- **S2** (2026-10-24): Secrets are never stored and never put into a view or a room frame. Views are validated against schemas without secret fields, and a sentinel test runs over every view and frame. _Reason:_ A leak is the worst failure of this game (05 §3).
- **S3** (2026-10-24): All round randomness comes from the seeded DRBG. `Math.random` is banned by lint in `packages/` and `games/*/src`. _Reason:_ Predictability and verifiability (05 §4).
- **S4** (2026-10-24): No latency compensation. _Reason:_ It would trust client-reported or inflatable times (05 §7). See R3.
- **S5** (2026-10-24): Abuse signals (cooldown rejections, guesses at bot-like timing, shared IP or device in one match) only raise a score for moderators. There are no automatic sanctions. _Reason:_ False positives must not remove honest players. This is Bingo's principle (Bingo 03 §13).
- **S6** (2026-10-24): _Superseded for the host by O16 and S10 (2026-10-26)._ The host and admins see only the spectator view of a running round. _Reason:_ Nobody inside the app can learn a running secret (M10).
- **S7** (2026-10-24): Frost-held answers are not part of any state answer until they are delivered. _Reason:_ Otherwise a state request would skip the delay (M9).
- **S8** (2026-10-24): The handoff claim `links` carries only the facts "telegram" and "discord", never handles. _Reason:_ Data minimisation (Bingo 03 §19).
- **S9** (2026-10-24): Each round queue has a bound (5 000). Beyond it, guesses are refused with `ROUND_BUSY` and start no cooldown. _Reason:_ A flood against one round cannot exhaust memory (M7).
- **S10** (2026-10-26): When a round runs, the host gets the same player view as every player and plays on the roster (O16); admins and others who are not on the roster get the spectator view. The host menu holds controls, never a secret. _Reason:_ Nobody inside the app can learn a running secret (M10): the host's view is a player view and has no secret field.
- **S11** (2026-11-12): Seasonal Mind Games: the server alone holds the live state. Before a round ends no view, state answer, frame, acknowledgement, admin or public route, host control, log line or metric carries anything younger than the delay, and pre-picks reach only their owner; choices after the join time or the play's end are refused at the server's receive time. _Reason:_ Its live state is its secret (05 §3.2, M17, M18); tested by P7, MG1–MG7 and the early-read tests (09).

- **S12** (2026-11-22): A host's round command over the socket needs a signed-in account that is the match's host. Before, the check compared the match's host with the session's account, both of which can be null: a guest could start, end or abort the rounds of a match whose host account had been deleted (`created_by` set to null). HTTP already refused a session without an account. _Reason:_ Found while building O130; the fix changes nothing for a real host. _Applied in:_ apps/server realtime/intents.ts `hostRound`; test/limits.integration.test.ts

## 4. Rejected approaches

- **R1** (2026-10-24): A global tick or turn-based rounds in which all players guess at once _Why rejected:_ Excluded by O3.
- **R2** (2026-10-24): Holding a guess sent during the cooldown and firing it when the cooldown ends _Why rejected:_ It would make server timers part of the receive order, and it hides the cost from the player. A refused guess is sent again by the player.
- **R3** (2026-10-24): Latency compensation (ordering by client send time or measured round trip) _Why rejected:_ Client times and round trips can be faked or inflated, which would turn a physical disadvantage into a cheat (05 §7).
- **R4** (2026-10-24): Storing secrets in a column, even encrypted _Why rejected:_ Deriving them from the encrypted seed leaves nothing extra to leak or keep in sync.
- **R5** (2026-10-24): Bingo's off-the-aggregate path for high-frequency input (marks recorded outside the match queue) _Why rejected:_ A shared-secret win needs one total order over all guesses (O4).
- **R6** (2026-10-24): Forwarding intents between instances _Why rejected:_ A second ordering point (T13).
- **R7** (2026-10-24): _Superseded by T117 (2026-11-01)._ Building a general guess engine now _Why rejected:_ Decided when the second game starts (T21). Simplicity until a second game needs it (01 §3).
- **R13** (2026-10-24): A `perMember` team scoring option _Why rejected:_ The owner decided `wins` with 1 point (O12); a second formula would be unused code.
- **R8** (2026-10-24): k6 for load tests _Why rejected:_ See T9.
- **R9** (2026-10-24): Client-side cooldown or feedback computation _Why rejected:_ Server authority (S1, Bingo 03 §1).
- **R10** (2026-10-24): One service per game _Why rejected:_ A modular monolith is enough and is simpler to run (Bingo 02 §1).
- **R11** (2026-10-24): Redis from day one _Why rejected:_ No benefit at the launch size (Bingo 02 §9).
- **R12** (2026-10-24): Bingo's live-call link (`host_call_ref`) in v1 _Why rejected:_ Not part of the owner's decisions for this platform. It can return as its own task.
